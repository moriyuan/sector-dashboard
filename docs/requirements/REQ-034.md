# REQ-034 开盘啦盘中直播原文卡片与新消息提醒

[← 返回需求总览](../../开发需求与生命周期.md)

**状态：已开发** | 日期：2026-11-23 | 版本：v1 | 范围：现有独立预览；正式集成仍归REQ-018

## 目标与替换范围

用户要求删除“全市场观察”的原分析逻辑，改为每分钟获取开盘啦盘中直播最新文字直接展示，并在页面打开时提示新内容。

删除该卡片专用规则研判、时序推理/判断记忆、DeepSeek生成与发布、模型调度/预算、旧分析接口及前端入口；保留并拆出直播抓取、原文解析、存储等通用能力。不只是隐藏卡片或关闭模型开关。切换后此功能不再调用DeepSeek，清理无引用的专用代码和测试。其他业务使用的行情采集、历史快照/回放不误删，旧分析历史与需求归档保留；不删除用户全局模型密钥。

REQ-009改为直播历史浏览；REQ-010/011/012中这张卡片的旧分析链路由本条替代；分析深度专题保留历史档案，不再作为本轮继续开发任务。

## 已核验的数据通道

2026-11-23通过现有KaipanlaSource的ConceptionPoint / ZhiBoContent通道真实读取，单次约188ms，返回71条，当天最新发布时间15:00。此为单次接口延迟，不是全量页面刷新耗时或长期SLA，也不证明已取齐全天。

现有解析具备消息ID、发布时间、正文、题材及关联股票；独立直播任务已有雏形，但仍混在分析协调器中。开发需要将它变为不依赖模型、核心筛选或全市场慢刷新完成的独立任务。

## 刷新与可靠性

1. 后台每60秒查一次最新消息，复用现有开盘啦传输和限频通道；多页面只订阅同一后台结果，不各自请求开盘啦。与行情刷新并发，有独立超时/失败状态，不等分析完成。手动刷新合并重复在途请求。
2. 以交易日＋供应商消息ID去重，按供应商发布时间稳定排序；每轮取到已知游标，新增超过一页时分页补齐。核实接口分页语义，未证实则标历史覆盖不足，不能只取最后一条而丢中间消息。
3. 不按“发布时间在最近60秒”硬过滤：迟到消息照收并标“补到”。同ID正文修订保存版本并标“已更新”，不冒充另一条新直播。
4. 成功无新内容是正常状态：保留最新正文并显示“本轮暂无新直播”。超时/失败保留正文并标连接状态、最后成功查询时间；不能伪称旧正文为刚发布。
5. 持久化原文、ID、来源发布时间、首次接收、版本和查询状态；重启恢复游标。采用唯一索引避免每分钟重复存储，相同正文无变化不重复写历史。
6. 后台向前端推送轻量新消息事件（优先SSE，断线按游标补取；不支持时复用短轮询读取本地服务）。浏览器页面不直接调用开盘啦或持有凭据。
7. 接入现有交易时段调度并覆盖盘前/午间/盘后有效直播窗口，按来源真实发布时间核实边界；显示下一次查询状态。首轮实现沿用现有分钟任务启停策略，不能无证据跳过午间消息；需要扩展全天常驻时另记录调用量与范围。

从上游发布到发现通常要等0～60秒再加网络与处理时间，不称秒级实时。断网或电脑休眠后恢复补取，不保证休眠时仍收到通知。

## 卡片布局

卡片标题改为“开盘啦 · 盘中直播”，明确原文来源，不再显示系统推理或置信度。

- 顶栏：直播状态、最新发布时间、最后检查时间、未读数量、“开启桌面提醒”。
- 主体：最新一条完整原文，保持合理段落和行距；固定卡片高度，长文内部滚动，不省略正文。上游内容按纯文本/安全白名单渲染，外部链接不得注入脚本。
- 底栏：“上一条 / 下一条 / 回到最新”，历史时间列表可展开；显示当前序号和当天已获取条数，覆盖不完整时明确提示。
- 用户正在看旧文时，新内容只增加未读提示，不强制跳转；位于最新且未展开旧文时自动更新。多条同分钟返回全部入历史，不只保存最新那条。
- 关联股票只使用供应商返回的证券映射，可点击查看已有行情；直播观点标为“开盘啦原文”，不包装成系统自己的事实结论。

## 新直播提醒：页面内默认，桌面可选

**页面内通知**：右下角非阻塞浮层，展示发布时间、来源和完整正文，长文可滚动；支持关闭和“查看直播”。多条批量到达采用队列/条数导航，避免同时铺满屏幕；不使用阻塞式alert或另开窗口。首次打开只建立历史基线，不把已存在的71条逐一弹出；首次取数后发现的新ID才提醒，恢复连接的补到消息单独标识。

**桌面通知**：提供显式按钮，由用户点击后请求Notification权限。支持并获授权才发送，拒绝后不反复索取权限；不支持或非安全环境时保留页面内提醒，说明原因。系统可能截断长正文，因此桌面通知显示摘要，点击回到页面对应条目看完整原文。系统勿扰设置可能屏蔽提示，不能承诺必达。用户要求的“完整文字弹窗”由页面内浮层满足。

同一浏览器多标签页通过共享已提醒ID及主标签协调减少重复；后台事件持久化、断线恢复游标与前端去重配合。首次打开/刷新/跨日/旧文修订均不应产生历史弹窗轰炸。可关闭页面内提醒或桌面提醒，偏好持久化。范围仅限页面打开且设备正常运行，不新增关闭浏览器后的Web Push服务。

技术依据：[MDN Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API)、
[MDN Using Notifications](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API)。
目前尚未在用户当前内嵌浏览器验证权限支持与实际系统通知；开发后分别核验内嵌浏览器和可用桌面浏览器，不能把API存在当作通知已送达。

## 验收标准

- 同一来源时点的最新正文与开盘啦响应一致，能阅读完整长文、切换已获取历史，发布时间和接收/检查时间分开。
- 后端每分钟一次共享查询，行情慢、单股补数慢不会拖延直播；此功能无DeepSeek及旧规则分析调用。
- 首次加载不弹历史；单条新消息弹一次，同轮多条均可阅读；迟到、修订、重启、刷新、跨日、重复响应、多标签页、网络恢复和分页缺口有针对性验证。
- 卡片读旧文不被抢走；系统授权允许/拒绝/不可用均有正确反馈；页面内长文可滚动，桌面通知点击定位对应正文。
- 真实接口成功与失败均保留证据；测试用固定消息可验证去重，但不能冒称真实盘中新消息推送已验证。收盘后无新直播时，记录真实链路读取结果及受控注入的交互验证分别结论。
- 旧代码及任务清理检查通过，历史档案仍可追溯，其他行情模块正常。记录查询耗时分布、请求次数及存储增量，单次188ms不代替长期验证。
