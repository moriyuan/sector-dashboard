建立日期：2026-11-22。维护时区：Asia/Shanghai。当前版本：v1.2，新增近期前排核心与人工增删方案。

本次汇总最近围绕开盘啦取数、短线看盘界面、盘中分析和核心持续跟踪提出的需求。历史实现如实补录，不代表用户已验收或已允许提交；较早的其他项目模块不纳入本次汇总。

**当前没有任何条目被标记为“已开发”。** 大部分最近功能已在独立预览中实现并测试，但尚未正式合入项目。已有项目业务改动单独注明，不能与预览混为一谈。

## 一、需求执行规则

从本文件建立起，执行以下流程：

1. 用户提出需求，先进行只读调查、问题分析和方案推导。
2. 在本文件登记编号、需求、方案版本、范围、数据、前端反馈、验收标准及剩余问题，状态为“方案待确认”。
3. 用户明确确认方案后，登记确认依据，转为“已确认，待开发”。方案确认不等于提交或部署授权。
4. 开始修改功能代码前先同步远程 `main`，记录同步结果和基线；不得覆盖既有未提交内容。同步失败时，仅能在用户已授权的例外范围内继续。
5. 开发期间更新实际实现与状态；发生实质范围变化时更新方案并重新确认新增部分。
6. 实现完成后记录测试、实际前端入口、数据限制和待验收项。测试通过后转为“实现完成，待验收”。
7. 用户验收通过后转为“验收通过，待提交”，仍不自动提交。
8. 用户明确要求提交时，只对本次实际完成、验证且纳入提交的需求更新“已开发”，与代码一起提交。提交结果及哈希单独登记；提交失败则回退状态并记录原因。推送只能到远程 `chenjuyin`。

新需求编号不复用。原需求的重大修订保留版本与替代关系。已确认范围内的实现修正不需要逐行重复确认；未经确认的新增功能不能借机开发。

### 生命周期状态

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| 方案待确认 | 需求及方案已登记，未获开发确认 | 等待用户明确确认 |
| 已确认，待开发 | 用户确认了指定范围和方案版本 | 同步 main，记录基线后开发 |
| 开发中 | 正在实现已确认范围 | 完成功能和必要验证 |
| 实现待复核 | 历史代码存在，但本次尚未核实全部验收项 | 补核验，不宣称交付完成 |
| 实现完成，待验收 | 已完成所列实现范围与测试 | 用户查看结果并验收 |
| 验收通过，待提交 | 用户已验收，尚未授权提交或提交未完成 | 等待提交指令 |
| 已开发 | 用户要求提交后，本次需求已随代码完成提交 | 记录提交结果；推送/部署另记 |
| 暂停／已取消／已替代 | 用户暂停、取消，或明确改用其他方案 | 保留原因、时间及替代编号 |

“已开发”不自动代表已部署，也不代表所有上游字段持续可用。预览实现与正式项目集成分别验收。

## 四、已实现需求及验收细则

### REQ-001 开盘啦 SDK 对比融合与可靠取数

- 目标：对比用户提供的 SDK 与项目原渠道，兼顾覆盖、延时、稳定性和安全，拒绝以返回成功冒充数据完整。
- 历史方案／现有实现：项目中有分页、日期及数量校验，涨停全梯队，行情与情绪、回撤个股、核心盘口、板块分时和复盘入口；传输层限制上游地址、验证 TLS、复用连接、限速、有限重试、冷却与超时预算。
- 位置：`backend/sources/kaipanla.py`、`backend/sources/kpl_transport.py`、`backend/kaipanla_live.py`；对比资料在 `work/sdk-review/`。
- 验收：跨日错数据拒收；分页去重且总数可核验；失败不覆盖成功记录；临时错误有限重试；异常与未知字段有明确状态；前端读取缓存不会为每个页面重复采集。
- 当前结论：代码和对比资料存在且尚未提交。本次为文档整理，未重跑正式项目全部验收，所以状态保留“实现待复核”。项目 README 仍描述五分钟链路和后端能力，不能据此声称正式界面已有新版预览功能。

### REQ-002 面向短线的高密度看盘布局

- 目标：围绕连板、核心、板块强度、赚钱／亏钱效应及盘面演绎组织信息，参照用户提供的终端式布局。
- 实现：深色多区布局，包含市场概况、板块强度、板块成员与个股详情、日内核心前排、涨停梯队、涨停时间流和全市场观察。
- 位置：预览 `terminal-template.html`、`fast-preview.py`、`analysis-card.*`。
- 验收：关键模块可同时定位；模块标题和数据可读；板块筛选、个股选择与详情可用；不重复堆叠同一梯队。
- 限制：预览布局不是正式 React 前端已完成集成的证据。

### REQ-003 涨停时间流、全梯队与去重复模块

- 目标：今日涨停按时间查看；单独完整展示一板、二板、三板、四板及更高梯队，每级内部也按时间排序；移除重复的上方梯队。
- 实现：根据最高板数取齐梯队，按 `limit_timestamp` 排序，代码用于同时间稳定排序；时间流与梯队分别承担“先后过程”和“高度结构”，不再重复放一个概要梯队。
- 位置：预览 `fast-preview.py` 及模板渲染；源字段来自项目 `fetch_limit_pool`。
- 验收：总数与完整涨停池核对；同梯队时间排序正确；高于四板的个股不遗漏；长列表可滚动。
- 口径：供应商时间尚不能确定为首次封板还是最近封板，显示为“涨停时间”，不宣称是精确首封事件。

### REQ-004 深色可读性与独立滚动

- 目标：修复黑色文字在深色背景不可读的问题；核心前排与涨停时间流不因成员增加被截断。
- 实现：显式文字颜色、深色表单与状态颜色；核心列表、时间流和分析正文有独立滚动区域，兼顾窄屏。
- 位置：预览模板、`analysis-card.css`、`ten-day-core.js` 和 `fast-preview.py` 样式。
- 验收：板块名、股票名、数值和输入控件清晰；底部成员可达；滚动单个区域不丢失选中状态。
- 证据：浏览器检查覆盖字体颜色、列表滚动、桌面与窄屏展示。

### REQ-005 手动刷新与低等待体验

- 目标：右上方可手动更新，避免取数期间页面一直空转；显示采样时间与更新状态。
- 实现：手动请求快速响应、后台分模块采集并渐进发布；先展示核心行情，较慢的报价等补充数据继续获取；已有请求合并、手动请求短冷却；失败保留旧结果及原时间。
- 位置：预览 `RefreshEngine`、`refresh-bridge.js`。
- 验收：按钮操作不阻塞读取已有行情；慢模块不拖住已成功模块；重复点击不重复整轮采集；缺失、过期、失败不冒充实时成功。
- 限制：没有承诺固定毫秒延时；网络与上游响应会变化。模型耗时也不等于行情获取耗时。

### REQ-006 每一分钟自动刷新

- 目标：把先前五分钟的预览采集改为一分钟。
- 实现：已验证交易日的交易时段按分钟时间格运行；同分钟避免重复；午休、收盘及非交易日暂停；新交易日先核验。
- 位置：预览 `fast-preview.py`，`REFRESH_SECONDS=60`。
- 验收：每个时间格最多一次计划触发；手动刷新与自动刷新不产生重复任务；休市不伪造“今日实时”；新交易日不借用昨日数据作本轮成功。
- 限制：包含开收盘检查点的时间格测试为242个，不能当作每个交易日必然采集242轮的保证。正式项目的五分钟链路尚未同步修改，见 REQ-018。

### REQ-007 存储、去重与失败保留

- 目标：一分钟采集能够追溯，避免每轮无差别重复存储；缓存失败不能覆盖可用数据。
- 实现：SQLite WAL；行情按内容哈希去重、zlib 压缩；每轮保存独立时间与清单；分析保存输入摘要及压缩输入、正文、采样和生成时间；报价与模型预算分别存储。
- 位置：预览 `refresh-history.sqlite3`、`analysis-history.sqlite3`、`core-quotes.sqlite3`、`model-budget.sqlite3`。
- 验收：重启可恢复；旧记录不被新结果改写；同日旧数据回退保留原时间；不可跨日冒充新数据；存储接口可查看压缩量与帧数。
- 限制：当前保留全部记录，尚无自动清理、归档周期或容量上限策略。若要求自动清理，先登记独立需求和保留期限，不自行删除历史。

### REQ-008 十日涨幅前五合入核心前排

- 目标：十日涨幅排名前五与日内核心前排合并，不另建重复股票池；可放在后方并滚动查看。
- 实现：验证最近十个交易日区间及榜单排序、重复和数量；将前五与当前前排按代码去重合并，显示排名、区间涨幅和来源口径；可进入详情。
- 位置：预览 `ten_day_source.py`、`ten-day-core.js`、刷新补充数据任务。
- 验收：使用十个交易日而非十个自然日；重复股票不占两个名额；五只都能滚动到；缺失榜单不补造排名。
- 运行限制：2026-11-20 已保存样本中该榜因交易日序列核验失败未取得有效前五，新版回放明确显示无已核验成员。代码已实现不代表任何日期都能拿到有效榜单。

### REQ-009 直播文字与全市场观察历史

- 目标：参考开盘啦直播的短线观察方式，把本轮发生的变化、意义和后续验证写入有限空间的观察卡片，且不拖慢行情。
- 实现：独立拉取直播，按编号去重；保留发布时间和系统收到时间；行情分析后台运行；卡片支持日期、上一条、下一条、时间选择、最新记录、正文滚动和数据依据。
- 位置：预览 `market_analysis.py`、`analysis-card.*`。
- 验收：刷新行情不等待直播；历史阅读位置不被新报告抢走；列表可分页访问；直播线索明确归因，不被当作已核验盘口事实。
- 限制：接口窗口不保证捕获全天每条直播；历史条目附带的动态行情不能当成当时的价格；不进行模型自动训练。

### REQ-010 短线时序、事件与判断记忆

- 目标：从静态统计提升到盘面过程，识别局部走强与整体修复的区别，并能修正旧判断。
- 实现：比较实际可用的一／五／十五分钟窗口和当日首个可用样本；记录前排退出、新入池、亏钱扩散、修复线索和假设状态变化；保存支持、反证、确认与失效条件。
- 位置：预览 `tape_intelligence.py`。
- 验收：缺样或午休不硬拼窗口；先后不冒充因果；前一轮“获支持”可以被新反证降为“承压”；未继续扩张不自动等于失效；模型历史结论不升级为事实。
- 限制：首次可用样本不一定是开盘；目前阈值是观察规则，不是验证过收益的交易信号。真实回放尚无“获支持后撤回”的实例，相关状态变化由构造测试验证。

### REQ-011 异步模型研判与校验

- 目标：补足解释深度，围绕核心、连板、板块扩散、情绪与反证进行受证据约束的推断。
- 实现：DeepSeek 接收结构化事实、时序事件、前次假设、直播摘录与缺失范围；返回解释、支持／反证引用和观察条件；检查格式、引用、输出完整性及部分不支持的表达。模型后台运行，一个正在分析的任务之外只保留最新待处理快照。
- 位置：预览 `model_reasoner.py`、`AnalysisCoordinator`。
- 验收：模型超时、失败或校验不通过时行情仍可用；旧结果不覆盖更新时点；密钥不进入前端或历史库；采样时间与生成时间区分。
- 证据：真实历史样本调用成功，单次约12.1秒；该结果仅说明联调成功，不代表固定耗时或分析正确率。行情非交易时段未做下一交易日持续运行验证。
- 频次以 REQ-012 为准。结构检查不能保证语义或因果完全正确，不能声称模型绝不会产生幻觉。

### REQ-012 降低模型调用频次与费用

- 目标：一分钟刷新行情不必一分钟调用模型，控制费用并保留解释连续性。
- 当前方案：行情和本地证据分析仍每分钟；模型常规十分钟复核；重要事件提前触发也至少间隔五分钟；失败冷却十分钟；每日最多三十次，同时受四十万保守预留 token 预算单位约束。
- 事件范围：普通新增封板不单独提前触发；前排退出、判断状态变化、亏钱效应扩散等达到重要性门槛时可提前复核。预算或冷却限制优先于触发。
- 前端：未调用模型时保留最近一次成功研判，标原采样时间与“本轮未重新推理”；展开的是旧研判原证据，不把引用套到新数据上。
- 验收：重启后冷却和预算仍有效；普通事件不能绕过十分钟；重要事件不能绕过五分钟；日上限覆盖人工历史验证；旧研判不跨日伪装为新判断。
- 边界：显式执行人工模型验证脚本可以跳过冷却，但不能跳过日预算。预算采用保守估算，不是实际账单金额；本次降频验收未新增付费模型调用。

### REQ-013 核心池档案与持续跟踪

- 目标：股票一旦入选观察核心，即使离开涨停池或后续走弱也保留，记录加入原因、时间和后续表现。
- 入选范围：当前日内前排八只；至少二板的全部连板观察和全部最高空间板；封板数量前三题材各取最早封板的前三只；已核验十日榜前五。按代码合并，保留累计原因及各原因加入时间。
- 持续记录：加入时间、核验时间、历史最高板数、是否仍在涨停池、有效报价、较首次有效报价的变化，以及最近二十次采样状态／报价变化；完整过程随每轮记录保存。
- 取数：独立后台补查报价，每轮最多六只，优先池外历史高位并轮换；报价必须在分析时点前已收到，源时间不超过两分钟。全池不保证每分钟都有新报价。
- 验收：超过八只的最高连板个股不遗漏；退出封板仍在池；缺价格不显示零或收益；旧报价不当作本轮新价；重启后可恢复同日档案。
- 真实例子：2026-11-20 14:49 记录中，华微电子在14:48样本已不在涨停池，仍保留跟踪。没有当时有效报价，明确显示缺失，不补造跌幅或跌停状态。
- 限制：当前是日内持续跟踪，完整跨日核心库见 REQ-019；规则选出的前排不等同已经确认的龙头。

### REQ-014 覆盖范围与缺失字段反馈

- 目标：用户能在界面看见实际观察了什么、缺什么，不能只在后台实现或只口头说明。
- 实现：全市场观察展示持续观察数量和池外数量；“核心跟踪”提供逐股明细；日内核心前排标题旁增加“持续跟踪”入口；“观察范围与尚未接入项目”列出覆盖情况。
- 缺失展示：有效报价、观察期比较基准、封单金额、个股资金流、精确炸板次数／时刻、跌停状态等按实际可用性标记；模型输入包含缺失清单，部分捏造表达会被拒绝。
- 验收：未知不是零；不在涨停池不等于跌停；不能把采样中消失与再出现写成精确炸板、回封事件；旧版历史无明细时明确提示，不虚补。
- 限制：“未接入／未核验”是程序当前能力边界，不是宣称供应商没有这些数据；精确补齐见 REQ-022。

### REQ-015 时点回放与验证隔离

- 目标：以当时能够得到的信息检验分析，避免未来数据污染历史判断。
- 实现：输入按时间排序；直播同时限制发布时间和首次接收时间；历史报价也检查可用时间与新鲜度；原始实时记录、离线回放、真实模型历史验证分别存储和展示。
- 前端：实时记录／V1历史回放／历史模型验证三种模式，记录明确标明日期与来源。
- 验收：原始报告不可被回放改写；时间与历史分页正确；不能以今天报价填补当年／当日历史缺口；回放本身不调用付费模型。
- 当前证据：124条历史快照，其中11月20日121条；识别21条结构变化事件；证据引用错误和未来时点证据检查均为0。观察对象最多17只；真实回放撤回“获支持”实例为0，不能据此宣称预测有效。

### REQ-016 最近交易日恢复

- 问题：周末重启预览可能退回较旧的初始样本。
- 实现：无当日存档时恢复不晚于当前日期的最近交易日存档；不将旧日各模块缓存复用为今天成功取数。
- 验收：周末恢复最近交易日而非旧种子；仍标历史日期；非交易时段不自动刷新；跨日核验规则不被绕过。

### REQ-023 第一项：完整观察对象与持续核心池

**目标与问题。** 分析不能只看当前涨停名单和十日涨幅前五。需要同时看接力收益、历史核心的亏钱效应、当日封板扩散、容量载体及全市场背景，避免弱股退出列表后被系统“遗忘”。观察候选与已确认龙头应分开，不能由规则排名直接授予龙头身份。

**观察对象及需要的数据。**

| 观察对象 | 必须回答的问题 | 数据与口径要求 | 当前状态 |
| --- | --- | --- | --- |
| 昨日涨停、昨日连板股 | 今日是否有溢价，晋级与断板情况如何，接力环境是否恶化 | 固定昨日样本名单、昨日板数、昨收、今开、当前有效价格、今日状态；开盘溢价与当前溢价分开，统计注明有效样本与缺失数 | 未建立完整昨日样本跟踪，关联 REQ-019 |
| 前期高位股、昨日核心 | 是否继续补跌、止跌、反包；旧方向亏钱效应是否延续 | 历史核心身份、首次入选原因、过去高度、逐日行情与调整口径；不得按今天强弱回头筛昨天核心 | 当前只有日内累计身份，跨日未齐 |
| 当日封板、炸板、回封个股 | 封板是否稳定，新增封板是否获得跟随 | 完整涨停池、采样时间、有效盘口；精确炸板／回封需要可核验事件流，不能只用名单变化代替 | 有完整池和采样进出；精确事件未核验 |
| 板块核心、成交额靠前个股 | 小票冲板时，大成交额载体是否同步增强 | 板块成分及归属版本、成交额排名、价格和量能连续数据；“成交额核心”与“涨停前排”分别入选 | 有板块封板前排；容量核心未独立筛选 |
| 十日强势股、趋势核心 | 赚钱效应在连板与趋势之间是否转移 | 十个交易日区间榜、榜单范围和调整口径、连续价格／成交；两类样本用各自规则，不等同十日排名就是趋势核心 | 十日榜接入有校验；趋势核心未齐，且部分历史日缺榜 |
| 指数、量能、上涨覆盖面 | 局部拉升是否扩散到市场，指数与情绪是否背离 | 同步指数、成交额／量能、涨跌家数、涨跌停与炸板统计；指数贡献需要成分权重等额外证据 | 有广度、部分量能和板块变化；完整贡献归因未齐 |

**核心档案的开发思路。**

1. 分离“本轮候选”“持续观察成员”“当前市场状态”。本轮不再满足入选条件，不等于从持续观察池删除。
2. 以股票代码及市场作为身份，记录首次加入时点、信息首次可用时点、入选类别、理由及证据、角色变化、最近有效报价、首次有效报价、当前状态和最近核验时间。一只股可有多个入选理由，增加理由不能覆盖原始加入时间。
3. 日内持续跟踪沿用现有实现；跨日扩展需要单独定义保留期限、归档／退出条件和重新入选规则。期限与规则须确认，不能默认为无限保留或跌停即删除。
4. 后续表现区分当日涨跌幅、相对首次有效报价变化、相对昨日基准的溢价。没有入选时价格，不得把首次补到的价格伪称入选价；跨日比较先明确除权等调整口径。
5. 使用已核验跌停价或逐股跌停名单判断跌停，不能统一按跌幅百分比猜测不同证券的涨跌停限制。只有池状态时，显示“不在当前涨停池，继续跟踪”。
6. 给每个必需字段保存来源、源时间、收到时间和质量状态。缺失原因至少区分未接入、来源未返回、超时、过期和未核验，不用空字符串或零混淆。
7. 扩大候选数量后优先复用已取得的有效批量数据，再对高风险池外核心、重要板块载体及轮换样本补查。当前六只补查预算不能被悄悄放大；覆盖不足要显示，新增调用成本须确认。

**前端反馈。** 继续使用“日内核心前排 → 持续跟踪”和“全市场观察 → 核心跟踪”，不重复新增一份涨停梯队。观察池可按角色、板块、池内／池外、缺失数据筛选；逐股展示入池档案、有效报价时间、后续变化和缺失原因。显示覆盖数量及统计分母，明确哪些类别未接入；若后续接入跨日身份，显示该身份来自哪一天。

**验收标准。** 曾入池个股走弱、离开涨停池或被证实跌停后仍可查询；重启不丢失档案；同股多原因不重复计数；昨日池不被今日幸存名单重写；缺价时不产生零收益；回放中不使用之后才取得的字段；页面能直接看见尚未覆盖对象。

**已有与待补齐。** REQ-013、014 已覆盖日内档案、保留、部分补查和缺失展示；昨日样本、跨日核心、容量／趋势核心、完整指数观察依赖 REQ-019～022。完整父需求尚未验收，不得用“持续跟踪已实现”代替全部观察对象已齐备。

### REQ-024 第二项：连续行情整理成事件证据包

**目标与问题。** 模型应收到盘面如何变化的证据，而不只是每轮一张排行榜。事件包要能支持区分局部题材扩散、整体情绪修复、轮动和亏钱效应扩散，同时保留不能判断的部分。

**模型分析一次所需的上下文。**

| 内容 | 拟形成的材料 | 缺失时的处理 |
| --- | --- | --- |
| 当前市场概况 | 市场广度、量能、涨跌停、炸板率、连板高度与板块集中度 | 按字段标质量，不跨日借值 |
| 一／五／十五分钟变化 | 起止样本、真实间隔、涨跌家数变化、封板增减、板块变化 | 缺足够样本时不生成该窗口，午休不伪装连续交易分钟 |
| 当日关键时间线 | 事件类型、首次发现、涉及对象、支持／冲突证据及重要性 | 缺精确源时刻时只写采样发现时刻 |
| 核心与主要板块的连续表现 | 入池后状态／价格路径、板块内新增封板、容量成员是否同步 | 未覆盖成员不得写成全板块结论 |
| 新增直播 | 去重编号、原文摘录、发布时间、首次收到时间、来源属性 | 过晚收到的文本不能用于更早回放；未核验的直播仍是线索 |
| 上轮判断与条件 | 判断标识、原依据、待验证条件、上轮处理和本轮规则检查结果 | 没有上一判断时明确是初次观察 |

**开发步骤。**

1. 对每轮已验证输入建立稳定快照标识。变化计算引用精确起止快照，不把不同日期、不同统计范围直接相减。
2. 定义事件记录：标识、对象、类型、源事件时间（可空）、首次发现／可用时间、起止快照、变化值、证据标识、质量状态和重要性。标签应描述观察事实，例如“退出完整封板名单”，而不是直接写“资金出逃”。
3. 在现有新增／退出封板、广度变化、跌停扩散基础上，按实际数据逐步补充板块内扩散、核心与容量成员背离、最高高度变化等事件。没有对应数据时不生成该类事件。
4. 对同一事件跨轮去重，保留状态更新；重要性排序用于选择本轮重点，原始事件仍可追溯。事件数多不等于分析质量好，不能为了每轮有新标题放大噪声。
5. 对直播使用已消费编号／时间游标识别新增内容，将其标为供应商观察，与结构化行情核对；矛盾时同时保留差异，不让文字覆盖行情。
6. 在模型调用前构建有体积预算的证据包：当前概况、窗口变化、重要事件、核心与板块路径、近期直播、旧判断和缺失列表。压缩时保留反证、来源与时点，不只保留上涨线索。
7. 跨模块的证据标识应包含快照或事件归属，避免多轮都叫同一个“板块／涨停”引用而误指向新的数值。保存实际送入模型的证据包便于复核。

**前端反馈。** “演绎”按时点展示事件，可查看窗口、涉及个股／板块及数据依据。显式区分“源事件时间”和“采样发现时间”；点击结论能定位其依据。完整日内记录可分页查询，短卡片只展示最近片段但不能使较早过程无法访问。

**验收标准。** 五分钟窗口必须展示实际比较的起止时点；同一事件不被每分钟重复当作新事件；失效、缺样和直播冲突可见；细粒度先后证据缺失时不能得出谁先带动谁；同一输入与同一规则版本产生可重现的事实事件；模型上下文不包含采样之后才可用的信息。

**已有与待补齐。** 已有窗口、部分结构变化、事件片段和直播时点校验；未完成全部核心／容量成员路径、统一事件数据协议、完整事件查询及新增直播游标等完整设计。现有模型包不能被称为已包含全部连续盘口。

### REQ-025 第三项：保存市场判断并逐轮验证

**目标与问题。** 持久化的不仅是上一段文章，还应包括能被后续行情检验的假设。系统每轮必须回答：原判断是否仍成立、新增什么证据、哪些条件兑现或失效、为什么维持或修改。

**拟保存的判断结构。**

| 字段 | 用途 |
| --- | --- |
| 判断标识、版本、创建与更新时点 | 将连续判断串联；保留修订前版本 |
| 作用范围 | 全市场／板块／个股／角色，防止局部结论外推 |
| 判断内容与类型 | 如“某方向存在局部修复迹象”，始终标记为推断 |
| 支持证据与反证 | 各自引用具体快照或事件，能追溯原始时点 |
| 待验证条件 | 观察指标、对象范围、比较基准、窗口、判定方法 |
| 失效条件 | 什么可观察事实足以要求下调或撤回，不只写空泛的“关注持续性” |
| 条件检查结果 | 成立／不成立／未知／过期，并记录本轮依据；未知不当作否定 |
| 本轮处理与解释 | 维持、加强、下调、撤回或待验证，并注明新证据 |
| 复核类型 | 本轮规则复核／本轮模型复核／沿用旧模型文字，不能混称 |

**开发步骤。**

1. 将“行情事实”“规则派生假设”“模型解释”分层保存。模型旧结论永远不能作为后续行情事实引用。
2. 把可计算的条件表达成受限制的规则结构，例如比较某板块封板数、核心是否仍在池、跌停是否增加、广度是否改善。条件来自受控指标和算子，不执行模型返回的任意代码；具体阈值和持续轮次需验证并确认。
3. 每轮行情到达后先由本地规则检查有效判断的支持、反证和条件，无需每分钟付费调用模型。把本轮检查结果交给下次模型，而非让模型从旧文章自行猜测。
4. 用有依据的状态转换记录判断演变。反证出现时允许下调或撤回；指标没继续上升不必自动推翻原判断；数据缺失或窗口过期时转为待验证，不静默判为修复失败。
5. 同时容纳多个方向或互相竞争的解释，区分一个题材局部修复与市场整体退潮。轮动时为新方向建判断，不能直接改掉旧方向名称来伪造连续性。
6. 保留每次处理前后的状态、原因、条件结果和证据版本。重启恢复时不得把已失效判断当作活跃判断，也不能因晚到分析把新版本退回旧状态。
7. 降频期间展示旧模型文字时注明原时间；当前规则复核可以更新，但不能写成模型已重新思考。

**前端反馈。** “判断”展示当前结论、上轮到本轮的变化、支持与反证、已满足／未满足／未知条件和下一步观察。可以展开判断历史，看到何时加强、何时承压、何时撤回，以及原因。用真实已观察到的状态描述过程，不预设市场必然走完“启动—扩散—分歧—失败”。

**验收标准。** 同一判断在新反证出现后能够明确修正；支持保持但暂无扩张时不无故重置；缺少报价不会被当作价格下跌；旧判断引用仍指向旧事实；一次模型失败不会删除已有判断；模型未调用时页面不显示“模型已复核”。

**已有与待补齐。** 已有题材假设、候选／获支持／承压／失效状态和旧模型保留；当前确认、失效条件主要仍是描述性文字，尚非通用的逐项计算条件。真实回放未包含“获支持后撤回”的充分实例，不能把构造测试通过说成市场效果已验证。

### REQ-026 第四项：模型负责解释，程序负责核对

**目标与问题。** 大模型用于提出有证据约束的解释、竞争解释和验证方法。程序负责取数、计算、口径、时点及可执行规则核对，不能把“接上模型”视为已获得正确行情推理。

**完整输出需要显式区分的五项。**

| 输出项 | 内容要求 | 不合格示例类型 |
| --- | --- | --- |
| 本轮最重要变化 | 选择本轮真正重要的变化，指向事件和比较基准；无重要变化可明确说明 | 每轮重写全市场概况，或拿旧事件冒充新变化 |
| 主要解释 | 说明变化可能意味着什么，限定作用范围及成立前提 | 少数强股直接外推全市场修复 |
| 另一种解释 | 提出与证据相容的替代解释，说明如何区分；证据不足时也可明确无法提出可靠替代解释 | 强行编造资金动机、消息原因或未观察到的过程 |
| 支持与反证 | 分别引用数据及直播线索，解释冲突；直播推测不当作事实 | 只引用支持材料，隐藏跌停扩散或板块整体走弱 |
| 下一步验证 | 可观察条件、加强或撤回判断的触发，以及数据不足时的处理 | 只有“关注持续性”，没有对象或验证标准 |

**开发步骤。**

1. 延续现有 DeepSeek 后台接入和思考模式，不在本次文档中擅自换模型或提高额度。为五项输出定义明确结构与提示词版本，保留对应实际输入包。
2. 将五项输出与 REQ-024 事件、REQ-025 判断及条件标识关联。解释只能引用给定事实；缺失的封单、资金流、精确事件只能作为未知限制说明，不能被模型补齐。
3. 程序生成或严格核对数值、股票代码、名称、日期、比较基准及单位。优先让模型引用结构化数值证据，由页面渲染具体数字；若未来允许模型写数字，须扩展中文数字、百分比／百分点、单位和归属检查，不能只检查某个数字是否在输入出现过。
4. 检查证据是否属于指定快照、事件和证券，是否在该时点已经可用，是否将缓存或晚到数据写成最新事实；引用能够存在但指向错误对象时也应拒绝。
5. 区分事实陈述、条件推断、供应商直播观察与模型假设。对“带动／导致”等因果表述要求相应贡献或细粒度证据，没有时降为相关性、先后线索或未知；语义检查不能保证全部错误都被拦截。
6. 校验结构、引用完整性、输出结束标志及缺失字段不支持的表达。失败时保留原分析及原时间，显示失败原因分类；不默认无限重试产生费用。
7. 保存模型版本、提示词版本、规则版本、采样及完成时间、输入摘要、使用量和校验状态。只保存最终解释与证据，不保存或展示原始推理链。

**前端反馈。** 观察卡片显示五项可折叠内容，默认突出本轮重点和主要解释，展开可看替代解释、反证和验证条件。明确“事实／模型推断／待验证”标签；引用可跳到对应证据。保留历史阅读位置，并分开显示依据的采样时间与分析完成时间。

**验收标准。** 输出结构能单独访问五项；明确存在另一种解释或“证据不足无法形成可靠替代解释”的理由；每个实质判断有依据及适用范围；未提供字段不被写成已知事实；旧数据、错误证券和未来引用被检查；失败有回退且不阻塞行情。通过结构校验不能显示成“判断已被市场证实”。

**已有与待补齐。** 当前结构为解释正文、支持引用、反证引用、观察选项与置信描述，有真实历史调用成功记录。尚无独立的“最重要变化／主要解释／另一种解释／下一步条件”完整五项模型结构，尤其不能把正文偶尔提到替代解释算作该功能已经落实。现有数字、表达和引用校验也不等于完整语义核对。

### REQ-027 第五项：行情与分析独立运行及安全发布

**目标与问题。** 数据更新速度不由模型决定。行情、本地证据分析和模型研判采用不同节奏；延迟、失败、晚到结果和降频期间的变化都必须有明确处理。

**目标处理顺序。**

```text
每分钟取数 → 校验、保存快照 → 立即发布已就绪行情
                         → 本地计算窗口、事件与条件 → 发布本轮证据观察
新增直播、历史判断、重要事件积累 → 触发与预算检查 → 后台模型解释
后台结果 → 证据校验 → 按采样版本发布模型补充并存档
```

这描述目标架构，不代表现有实现已经把每个阶段都作为独立可发布版本。

**开发步骤。**

1. 沿用当前行情渐进加载和独立模型线程。进一步明确本地证据稿先发布、模型结果后补充的版本协议，不让同采样的规则观察也等模型完成后才落地。
2. 每个任务关联交易日、采样时点、快照标识、任务标识与规则／模型版本。实时指针按可用采样时点前进，而不是按哪个网络请求最后返回决定。
3. 模型较慢时维持“一个运行中＋最新待处理”的有界队列；可合并过时的分析请求，但行情快照和重要事件不能随之丢失。旧报告可存历史，不覆盖更新的实时结论。
4. 冷却期间把重要事件纳入待复核上下文，下一次调用一起评估；避免重要事件只出现一轮，恰好遇到冷却就永久漏掉。积累事件不能绕过调用间隔和预算。
5. 明确执行当前已确认的成本约束：行情／本地证据每分钟；常规模型十分钟；重要事件最短五分钟；失败冷却十分钟；每日最多三十次且受四十万保守预留 token 预算单位限制。预算不是账单金额，新增方案不得自动提高上限。
6. 没有值得调用的新变化时允许本地复核后维持判断，页面写“规则已复核”；若没调用模型，就写“沿用此前模型研判，本轮未重新推理”，不能为了符合模板冒称模型已复核。
7. 错误或预算耗尽时行情与本地观察继续，模型保留旧结果和原时间。重启恢复预算、历史和正确交易日；未来正式集成要统一调度，防止项目与预览同时重复取数或重复计费。
8. 分别记录行情首屏可用耗时、核心数据就绪耗时、本地计算耗时、模型等待／推理耗时及报告时效。不要用一个总耗时混淆取数慢与分析慢。

**前端反馈。** 显示行情采样时点、本轮证据观察时点、最近模型依据时点与完成时间；状态区分等待数据、本地已更新、模型处理中、冷却跳过、预算受限和失败保留。翻看历史时不抢回最新页；“最新”恢复跟随的是正确版本，不是最近结束的旧任务。

**验收标准。** 故意阻塞模型时行情仍按授权节奏更新，本地证据稿可独立发布；乱序完成的旧结果不覆盖新版本；大量触发不会积累无界队列；冷却期间关键事件可被后续复核；日预算和间隔在重启后仍生效；旧研判时间和当前行情时间不会混标。

**已有与待补齐。** 行情独立、渐进发布、慢分析不阻塞行情、最新待处理队列、历史排序与降频预算已实现。当前一条分析的保存通常仍在本轮模型步骤之后，尚未完整实现“本地证据稿先发布、模型补充后发布”的分阶段协议；冷却重要事件的持久待复核队列和正式项目统一调度也未齐。这些是补齐方案，不应勾为已完成。

### 原方案第六条：回放质量评估补充，关联 REQ-015

前五项是否提高分析深度，需要独立评价。现有124条回放验证了部分程序与时点行为，不能替代跨行情质量评估。

- 样本覆盖：选择修复、分歧、退潮、轮动等不同走势的交易日；固定样本与标注版本，分开调规则用样本和验收用样本，不能只挑适合当前规则的一天。
- 时点约束：每一轮只使用当时已经收到的信息；午后、收盘修订和晚到直播不能回填成早盘可知。未来行情只能用于事后评估标签，不能进入推理输入。
- 对照基线：比较原规则版、增加时序与记忆后版本、模型解释版；相同输入、时点与预算下评估，不能只看标题变化或文章长度。
- 评价维度：重要变化识别与延迟；“共振／主线／龙头”的误报；反证出现后的修正延迟；历史核心漏跟踪；无依据陈述、无效引用和未来信息使用；增加的有效解释与代价。
- 评价依据：开盘啦直播是参考观察，不是标准答案。需要明确事件标注依据，保留不同解释和人工复核结果；尚无可靠真值时不能给出伪精确准确率。
- 验收输出：案例清单、各维度结果、失败原因、版本对比和下一轮改进建议。修改提示词、阈值、入池规则或增加成本时，先更新对应需求方案并确认；不自动训练或自动改策略。

该补充的完整评估方案待确认；已完成的 REQ-015 时点回放基础状态保持不变。

## 七、REQ-028 近期前排核心与人工维护方案

### 1. 需求目标与栏目安排

- 今日前排：保留当前日内前排的查看能力；与近期池重合的个股可以显示对应身份标签。
- 近期前排核心：统一收纳多种近期强势身份、历史保留核心和人工指定核心，支持搜索、分类、滚动及详情。

### 2. 入池类别、依据与缺失处理

监管观察的接入需先核对开盘啦是否提供可追溯列表及对应来源；当前不能承诺已经取得。没有来源或有效期未明确时标注“来源待核验／有效期未明确”，不能因涨幅高就推断“正在被监管”，也不能把旧公告静默标为当前有效。人工备注只能标为人工备注，不升级为官方监管事实。

已有十日榜范围包含 ST 时，二十日榜应沿用同一范围或显式标明差异；不能无提示排除部分证券后仍称原榜前五。对停牌、样本缺失和价格调整口径单独标记，不用模型生成排名、反包次数或监管信息。

### 3. 主观类别的规则草案

以下是供确认的初始筛选定义，不声称是通用市场标准或已经实现；候选资格与用户认定的核心身份分开保存。

- **反复反包候选**：初步使用最近二十个交易日，至少出现两次独立的跨日恢复事件。一次事件暂定义为：曾收盘涨停，之后一至三个交易日没有收盘涨停，再次收盘涨停且收盘价收复前次涨停收盘价及间隔期最高收盘价。同一次再次涨停只计一次。若当日尚未收盘，只显示待确认候选，不能提前计入已确认次数。
- **高度活跃候选**：初步使用最近二十个交易日，曾达到四连板，或区间内收盘涨停至少五次。显示具体触发原因和日期。该规则只筛高位活跃对象；“抱团”仍以人工确认或后续专门规则标识，不把筛选条件直接翻译成资金行为结论。
- **趋势强势候选**：初步采用最近二十个交易日涨幅至少15%、最近已完成交易日收盘价高于十日均线且十日均线高于二十日均线、二十日均线高于五个交易日前的二十日均线。至少准备覆盖上述计算的二十五个交易日数据，并核验缺样与停牌口径。该条件仅用于候选筛选，不解释为买卖信号。
- 人工加入不受上述自动阈值限制；自动规则未命中也不能删除人工核心。后续调整窗口、阈值或筛选范围，先修改本条方案并记录版本。
- 规则结果不完整时显示覆盖情况，例如“历史涨停记录不足，反包类别暂不可用”，不能把“无法筛选”显示成“市场没有该类股票”。用户仍可在证券身份核验后人工加入。

### 4. 人工增加与删除

**增加。** 栏目工具栏提供“＋增加”。支持按代码或名称搜索，展示市场、代码和名称供选择；重名证券不得自动选错。用户可填入选理由、附加分类或备注。选择已有成员时合并人工身份，不重复新增一行，也不重置首次加入时间。证券身份暂时核验失败时保留输入并提示重试，不创建虚构证券。

**删除。** 提供逐行删除和“删除选中”按钮。删除含义是退出用户的“近期前排核心”观察池，并写入持久排除记录，而非仅隐藏当前页面一行。刷新、重启、跨日或再次进入自动榜单都不能自行把该股加回来。操作后提供撤销入口；另有“已移除”列表，可明确恢复。

**人工优先级。** 用户排除优先于自动规则；用户重新添加或恢复，才解除该排除。手动加入的成员跨日保留，直到用户删除。对于自动成员，名次下降或不再符合规则时，只把相应资格标为“历史入选”，不因走弱自动移出持续观察池；长期归档策略后续另行确认。

**范围与历史。** 从近期核心池删除，不改动原始行情、涨停全梯队、历史分析或已有入池档案。后台停止因该用户核心身份给予的重点补查；若它仍是全市场涨停或事件涉及股票，仍可出现在对应的全市场数据里。人工操作作用于当前管理名单，不能追溯改写历史回放时点的成员和证据。

### 5. 前端布局和字段

建议栏目头部为：`今日前排 | 近期前排核心`，右侧提供 `＋增加`、`删除选中`、`已移除`。近期栏目内有名称／代码搜索和类别筛选：全部、10日榜、20日榜、监管观察、反包、高度／抱团、趋势、人工加入、历史保留。

默认优先展示人工加入成员，再显示当前命中自动条件的成员，最后为仅保留历史身份的成员；不使用未经说明的“综合强度”分数替代这些明确分类。可以按涨跌幅、十日／二十日涨幅、加入时间排序，空值不当作零排序。

主表控制信息密度，包含选择框、股票名称／代码、身份标签、最新有效涨跌幅、十日／二十日涨幅、当前状态、数据时间和删除操作。原因、监管依据、区间日期、反包事件、历史最高高度、趋势计算依据、后续表现及缺失字段放入展开详情。列表独立滚动，人工加入后立即定位到该行。

监管依据显示可追溯来源和时点；人工标记与自动识别采用不同标签。未取得实时价格时显示“缺失／过期”及最后有效时间；不填零。该股若有多个身份，一行同时显示多个标签，筛选统计也明确是按类别计数还是去重股票数。

### 6. 数据与开发步骤

1. **源能力核验**：复查现有十日榜适配器，确认能否使用同一接口形式取得二十日区间；核验至少二十五个交易日的行情及涨停记录，以及监管观察来源。先做只读能力清单，不把未经实测的接口写成已接入。
2. **统一近期核心池**：将证券身份、自动分类结果、持续成员关系、人工覆盖规则、缺失状态分离。拟持久化成员、角色证据、人工操作记录与排除记录；具体表结构在实现时细化，数据库是权威来源，不只存浏览器缓存。
3. **跨日与迁移**：迁入原持续观察成员，保留其实际首次加入时间与来源。跨日沿用成员身份，新交易日补新行情；旧日价格始终保留旧时间，不能冒充今天更新。该迁移不等于已完成全部昨日涨停分析需求。
4. **自动分类**：按证券身份合并十日／二十日榜、监管观察、规则候选和已有核心；分别记录首次命中、最近命中、当前是否符合、规则版本及证据。自动更新与人工排除通过原子操作合并，防止刷新竞态把已删除股票重新写入。
5. **管理接口与界面**：增加证券搜索、当前名单、添加、移除、恢复和历史查询能力。写操作沿用本机来源／请求校验，重复点击幂等；批量操作返回实际结果，不显示未成功的假状态。添加无报价时先显示成员，再异步补查。
6. **模型与观察联动**：模型和核心补查读取统一有效观察池；输入包含人工／自动身份和证据时点，人工“看好／抱团”备注只是观察理由，不能作为已确认市场事实。历史回放按操作生效时间重建成员，不把今天人工加的股植入过去。
7. **交付与验证**：完成预览中的表格、详情、人工维护及自动来源状态后验收。正式项目迁移仍先同步远程 main，并走对应确认与测试流程，不自动合并或提交。

### 7. 刷新、性能与费用

- 行情刷新仍按一分钟；新增候选筛选和历史补齐独立运行，不能把全市场日线逐股请求串入每分钟主刷新。
- 十日／二十日榜拟在交易日首个有效轮次、盘中每十分钟和收盘有效样本刷新；日期和源口径不满足时保留旧榜时间并显示未更新。自动身份变更与成员保留分开。
- 反包／高度／趋势的已确认跨日条件优先用缓存历史数据，在新的有效日线到达后增量重算；今日盘中触发仅作为待收盘确认线索。
- 监管观察采用独立缓存，拟十分钟检查新记录，实际频率受合法可用渠道能力和限流约束；已移除成员不会因名单再次返回而重新入池。
- 人工增删立即更新本地名单，不等待模型；它本身不触发一次 DeepSeek 调用。名单增大不能自动增加模型调用频次、每日次数或既有 token 预算。
- 原六只核心报价轮换预算暂不扩大。显示本轮覆盖数和价格时效，人工新加入可进入下一轮优先队列；若需要全池逐分钟新价，再评估批量渠道与成本并单独确认。
- 成员、排除与操作记录使用持久存储，保留历史追溯；本次不自动删除既有行情、历史分析或核心档案。

### 8. 验收标准

1. 日内核心前排区域能切换“今日前排／近期前排核心”，旧“持续跟踪”入口同步调整，分析卡片与管理名单一致。
2. 十日和二十日前五都能按各自已核验区间显示；交集只占一行；任何来源缺失均有明确说明，未取齐不能宣称全类别已覆盖。
3. 监管事项显示来源、类型及时点；人工备注、高涨幅和普通异动不能冒充已核验监管事实。
4. 反包、高度和趋势候选可以按公开在页面上的规则重算；次数和日期有证据，不能把同日回封或尚未收盘的状态当作已确认跨日事件。
5. 添加支持代码／名称检索和去重；手动加入立即可见且刷新、重启、跨日不丢失；自动条件失效不删除人工成员。
6. 手动删除后刷新、重启、跨日及再次命中榜单均不会自动回来；明确恢复或重新添加后才能解除排除；删除与后台刷新并发也保持该规则。
7. 删除只改变当前用户观察关系，历史报告、真实行情和此前入池证据仍可回看；回放不被之后的人工操作污染。
8. 股票走弱、退出封板或被核验为跌停仍能持续观察，除非用户主动移除；缺失报价和收益显示未知，不补造不存在的数值。
9. 界面长列表可滚动、分类和排序正确；增删不等待取数或模型，自动分类不阻塞一分钟行情刷新，也不突破模型预算。
10. 对无法取得的监管／历史数据如实列为未覆盖。只有已确认范围实际达到验收标准时，才转为“实现完成，待验收”，不能只完成界面就标全部完成。
